### 0.1 Was TodoWrite tatsaechlich liefert

**Dieser Abschnitt ist Beleg, nicht Annahme. Er darf nicht ueberschrieben werden,
ohne die Quellen neu zu pruefen.**

Der echte Hook-Payload enthaelt pro Todo **genau drei Felder**:

```jsonc
{ "content": "...", "status": "pending" | "in_progress" | "completed", "activeForm": "..." }
```

| Feld | Zustand |
|---|---|
| `id` | **existiert nicht.** Nicht instabil — schlicht nicht vorhanden. |
| `priority` | **existiert nicht.** |
| `status` | nur drei Werte. **Kein `cancelled`.** |
| `activeForm` | existiert, kam in der Planung bisher nicht vor. Fuer das Board ohne Nutzen — `content` traegt die Information. |

Dazu die Tool-Beschreibung von TodoWrite selbst: *"Send the full list each call;
it replaces the previous one."* Es gibt kein Identitaetskonzept ueber Aufrufe hinweg.

**Quellen** (drei unabhaengige, exakt uebereinstimmend, Schema ueber Versionen stabil):
1. das installierte Claude-Code-CLI-Binary, Version 2.1.220
2. ein Reverse-Engineering-Repo fuer ccVersion 2.1.84
3. ein unabhaengiger Gist

Das Interface in `sync.ts:16-22` entspricht einer sehr fruehen, oeffentlich
kursierenden Fassung — nicht dem aktuellen Stand. Es wurde nie gegen einen
echten Payload validiert, weil `sync.ts` seit seiner Entstehung nie fehlerfrei
durchgelaufen ist.

**Drei Folgen, alle entschieden:**

1. **`source_id` faellt ersatzlos** aus Schema v3. Ein clientseitig erzeugter
   Content-Hash loest nichts: er aendert sich mit dem Content und ist damit
   funktional identisch zum bestehenden Titel-Matching. Mit den Daten, die
   TodoWrite liefert, ist die Identitaet eines Todos ueber Umbenennungen hinweg
   **prinzipiell nicht rekonstruierbar**.
2. **Priority-Uebernahme aus TodoWrite entfaellt** (Task P2-4 gestrichen).
   `priority` und `dueDate` bleiben echte sortierbare Spalten, werden aber von
   `planer` oder JoPa gesetzt.
3. **Der `cancelled`-Zweig** in `STATUS_TO_COLUMN` (`sync.ts:13`) ist toter Code
   und wird entfernt. Damit loest sich Einwand E-3 von selbst auf — der Fall
   "Sync schreibt ins Backlog" tritt real nie ein.

**Dokumentierte Einschraenkung, kein offener Bug:** Wird ein Task, der aus einem
Todo entstanden ist, im TUI umbenannt, erzeugt der naechste Sync einen zweiten
Task. Gehoert in README und CHANGELOG.

## 2. Paket 0 — Schema v3 und explizite Migration

Das riskanteste Stueck des Releases: eine irreversible Umformung fremder Produktivdaten (mindestens `/Users/joachimpaul/_DEV_/_PROJECTS/kanban-mcp/.kanban/board.db` selbst und jedes andere Board auf der Platte).

### 2.1 Zielzustand

**`.kanban/config.json`** — **entschieden (K-1)**:

```jsonc
{
  "name": "Kanban Board",
  "createdAt": "2026-03-03T12:59:44.202Z",
  "schemaVersion": 3,
  "columns": [
    { "id": "backlog",     "name": "Backlog",     "wipLimit": 0, "allowEntry": true,  "isTerminal": false },
    { "id": "todo",        "name": "Todo",        "wipLimit": 0, "allowEntry": true,  "isTerminal": false },
    { "id": "in-progress", "name": "In Progress", "wipLimit": 3, "allowEntry": false, "isTerminal": false },
    { "id": "review",      "name": "Review",      "wipLimit": 0, "allowEntry": false, "isTerminal": false },
    { "id": "done",        "name": "Done",        "wipLimit": 0, "allowEntry": false, "isTerminal": true  }
  ]
}
```

Zwei Festlegungen, die den Rest des Plans praegen:

**1. `position` entfaellt — die Array-Reihenfolge IST die Reihenfolge.**
Beim Einlesen wird der Array-Index zur Position. Damit bildet die Datei die
Vorwaerts-Regel direkt ab, und es gibt keine Positionsnummern, die von der
tatsaechlichen Reihenfolge abweichen koennen — ein Fehlerbild, das mit einer
`position`-Spalte frueher oder spaeter auftritt (zwei Spalten mit `position: 2`).
Eine Spalte verschieben heisst eine Zeile verschieben, im git-Diff sofort lesbar.

Konsequenz fuer den Code: `Column.position` bleibt als **abgeleitetes** Feld im
Domain-Objekt erhalten (der Rest des Codes rechnet damit), wird aber beim Laden
aus dem Index gesetzt und nie aus der Datei gelesen. `validateBoardConfig` darf
ein `position`-Feld in der Datei nicht akzeptieren, sondern soll es als Fehler
melden — sonst glaubt jemand, es haette eine Wirkung.

**2. `allowEntry` am Spaltenobjekt** statt separater Eintrittsspalten-Liste. Die
Regel gehoert zu der Spalte, nicht in den Code. Wer sich eine sechste Spalte
konfiguriert, soll nicht `task-service.ts` patchen muessen.

`done` steht bewusst auf `allowEntry: false` — sonst stuende die addTask-Hintertuer
zur Terminal-Spalte wieder offen, und die Regel "Abschluss nur aus Review" waere
mit einem einzigen `addTask({columnId: "done"})` umgangen.

Es gibt **keine** Uebergangsmatrix in der Config. Die Kettenregel ist aus dem
Index ableitbar (`zielIndex <= quellIndex + 1`).

**DB-Schema v3:**

```sql
-- entfaellt: DROP TABLE columns;

-- Nur ZWEI neue Felder. 'source_id' ist gestrichen — siehe Abschnitt 0.1.
ALTER TABLE tasks ADD COLUMN priority  TEXT;     -- 'high'|'medium'|'low'|NULL
ALTER TABLE tasks ADD COLUMN due_date  TEXT;     -- ISO-8601 Datum oder NULL

CREATE TABLE transitions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id     TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  from_column TEXT,                 -- NULL = Task-Entstehung
  to_column   TEXT NOT NULL,
  reported_by TEXT NOT NULL DEFAULT 'user',
  reason      TEXT,
  was_override INTEGER NOT NULL DEFAULT 0,
  created_at  TEXT NOT NULL
);
CREATE INDEX idx_transitions_task ON transitions(task_id, created_at);
```

`ON DELETE CASCADE` mit Bedacht: `deleteTask` loescht damit auch die Historie. Das ist gewollt — `foreign_keys = ON` ist bereits gesetzt (`db.ts:29`), also greift es auch.

`tasks.column_id` verliert seinen `REFERENCES columns(id)`-Constraint. SQLite kann Constraints nicht per ALTER entfernen → **Tabellen-Neubau** (siehe 2.3, Schritt 6). Das ist der eigentlich riskante Teil, nicht das `DROP TABLE columns`.

### 2.3 Migrationsablauf — verbindliche Reihenfolge

Neue Datei: `src/core/migrate-v3.ts` (nicht in `db.ts` — `db.ts` ist mit 173 Zeilen noch klein, wuerde aber mit der Migration ueber 300 wachsen und zwei Verantwortungen tragen).

```
 1. Board oeffnen, Schema-Version lesen. != 2  → Abbruch mit Erklaerung.
 2. Vorpruefung (read-only):
      - existiert Tabelle 'columns'?
      - Spalten-Datensaetze einlesen
      - Tasks mit column_id, die in columns fehlt  → zaehlen und melden (werden zu Waisen, das ist ok)
      - existiert config.json und ist valides JSON?
      - hat config.json bereits ein 'columns'-Feld? → dann ist ein Vorlauf abgebrochen (siehe 8.)
 3. BACKUP:  board.db → board.db.bak-v2
      - via SQLite Backup-API bzw. VACUUM INTO (WAL-sicher; ein blosses File-Copy
        waere bei aktivem WAL unvollstaendig)
      - existiert die Backup-Datei schon: NICHT ueberschreiben, sondern
        board.db.bak-v2.<timestamp> anlegen. Ein zweiter Lauf darf das erste Backup nie zerstoeren.
 4. config.json schreiben: Spalten aus der DB uebernehmen, schemaVersion: 3, allowEntry setzen
      - atomar: config.json.tmp schreiben → fsync → rename
 5. config.json neu von Platte lesen und verifizieren:
      - JSON parsebar
      - columns[] vorhanden, Laenge == Zeilenzahl der columns-Tabelle
      - jede id/position/wipLimit/isTerminal identisch mit der DB-Zeile
      - genau eine Spalte mit isTerminal: true
      → bei Abweichung: ABBRUCH. Die DB ist an dieser Stelle noch unberuehrt.
 6. DB-Transaktion (eine einzige, BEGIN IMMEDIATE):
      a) transitions-Tabelle anlegen + Index
      b) tasks_new ohne columns-FK, mit priority/due_date anlegen
      c) INSERT INTO tasks_new SELECT ... FROM tasks
      d) Zeilenzahl tasks_new == Zeilenzahl tasks pruefen → sonst ROLLBACK
      e) DROP TABLE tasks; ALTER TABLE tasks_new RENAME TO tasks
      f) Indizes neu anlegen (idx_tasks_column, idx_tasks_archived, idx_tasks_position, idx_tasks_source)
      g) DROP TABLE columns
      h) UPDATE schema_version SET version = 3
      COMMIT
 7. Nachpruefung: Tasks zaehlen, Dependencies zaehlen, mit den Werten aus Schritt 2 vergleichen.
 8. Bericht: "N Tasks, M Dependencies, K Spalten migriert. Backup: board.db.bak-v2"
```

Zu Schritt 6e: `PRAGMA foreign_keys` muss fuer den Tabellen-Neubau **innerhalb** der Migration ausgeschaltet werden (`PRAGMA foreign_keys = OFF` vor `BEGIN`, danach wieder ON), sonst kaskadiert `DROP TABLE tasks` die `dependencies`-Eintraege weg. Das ist die Falle, die diese Migration am ehesten still Daten kosten wuerde. Alternative ohne dieses Risiko: `dependencies` vorher in eine Temp-Tabelle sichern und nach dem Rename zurueckschreiben. **Empfehlung: beides** — `foreign_keys = OFF` *und* Zaehlpruefung in Schritt 7.

**Wiederholbarkeit:** Jeder Schritt prueft seinen Zielzustand, bevor er handelt. Bricht der Lauf nach Schritt 4 ab (config.json geschrieben, DB noch v2), findet der naechste Lauf ein config.json mit `columns` vor und ueberspringt Schritt 4, statt zu scheitern. Ein Lauf, der Schritt 6 vollstaendig durchlaeuft, ist idempotent, weil `schema_version = 3` in Schritt 1 sofort abbricht.

### 3.1 Neues Modul `src/core/transition-service.ts`

Kein weiterer Anbau an `task-service.ts` (304 Zeilen, naehert sich der 400er-Grenze). Verantwortung: Regeln pruefen, Pfade berechnen, Transitions protokollieren.

```ts
export interface TransitionCheck {
  allowed: boolean;
  reason?: string;          // handlungsleitender Text, nur wenn !allowed
}

export class TransitionService {
  canMove(task: Task, toColumnId: string): TransitionCheck
  canEnter(columnId: string): TransitionCheck          // fuer addTask
  canComplete(task: Task): TransitionCheck             // Task muss in Review stehen
  reconcilePath(fromColumnId: string, toColumnId: string): string[]   // NUR fuer Sync

```

**Regel Vorwaerts/Rueckwaerts** (aus dem Array-Index in `config.columns` abgeleitet, keine Matrix):

```
zielIndex <= quellIndex + 1   → erlaubt
sonst                          → abgelehnt
```

Rueckspruenge beliebiger Weite sind damit automatisch erlaubt. Gleiche Spalte (`zielIndex == quellIndex`) ebenfalls — no-op, kein Fehler.

**Sonderfaelle, die explizit ausgenommen werden** (sonst brechen bestehende Funktionen):

| Operation | Verhalten |
|---|---|
| `restoreTask` (`archive-service.ts:83`) | Ziel default `todo`. Ein archivierter Task hat keinen sinnvollen Kettenzustand → **keine Regelpruefung**, aber Transition mit `reason: "restore"` protokollieren. |
| `archiveTask` | keine Spaltenaenderung → keine Pruefung. |
| `reorderTask` | innerhalb der Spalte → keine Pruefung. |
| Waisen-Spalte (Spalte fehlt in config) | `quellIndex` unbekannt → jeder Move erlaubt, Transition mit `reason: "orphan-recovery"`. |

### 3.2 Ablehnungstexte

Nicht `Fehler: WIP-Limit erreicht`. Format:

```
Verschieben abgelehnt: "Backend-Migration schreiben" steht in Todo,
Ziel waere Review.

Die Kette ist vorwaerts strikt: aus Todo geht es nur nach In Progress.
```

```
  [a1b2c3d4] "Export-Service testen"        seit 4 Tagen  (backend)
```

**Alle Ablehnungen in MCP-Tools bekommen `isError: true`.** Ein Agent, der `content` ohne Fehlerflag zurueckbekommt, liest die Ablehnung als Erfolg.

### 3.3 `reportedBy` als Pflichtfeld

**Entschieden (K-3): `reportedBy` gilt nur fuer Transitions.** Kein `updated_by`
auf `tasks`. Begruendung: Feld-Diffs im Audit-Log wurden in der Grilling-Session
ausdruecklich verworfen ("dafuer gibt es git, keine halbe Versionsverwaltung im
Board") — ein `updated_by` waere der erste Schritt genau dorthin. Zusaetzlich
spart es ein Feld in der riskantesten Migration.

Betroffen: `kanban_add_task`, `kanban_add_task_checked`, `kanban_move_task`,
`kanban_complete_task`.

Nicht betroffen: `kanban_update_task`, `kanban_delete_task`, `kanban_init`,
`kanban_archive_tasks`, alle lesenden Tools.

`kanban_restore_task` erzeugt eine Transition (`reason: "restore"`) und bekommt
`reportedBy` damit automatisch — das war der einzige wirklich fragliche Fall.

Schema-Beschreibung wortgleich in allen Tools:


### 3.9 Sync-Umbau — `src/cli/commands/sync.ts`

Vollstaendiger Neubau. Der Datei-Zustand heute ist nicht rettbar (siehe 0. — sie laeuft nicht).

**a) Konstruktor-Fehler beheben:** `new TaskService(db, boardService, notesService)`. Das allein macht Sync wieder lauffaehig und sollte der *erste* Commit des Pakets sein, damit der Rest gegen einen funktionierenden Ausgangszustand gebaut wird.

**b) `TodoItem`-Interface auf das echte Schema korrigieren** (`sync.ts:16-22`):

```ts
interface TodoItem {
  content: string;
  status: "pending" | "in_progress" | "completed";
  activeForm: string;
}
```

`id` und `priority` entfernen — sie existieren nicht (Abschnitt 0.1).
`cancelled` aus `STATUS_TO_COLUMN` (`sync.ts:13`) entfernen — toter Code.
`activeForm` wird nicht verwendet; im Interface stehen lassen, damit klar ist,
dass das Feld bekannt und bewusst ignoriert ist.

**c) Matching — Content-Vergleich, gehaertet.** Das ist die einzige moegliche
Strategie; `source_id` ist gestrichen.

1. exakter Titelvergleich gegen `todo.content`
2. Vergleich gegen die 200-Zeichen-Kuerzung von `todo.content` (fuer Tasks, die
   beim Anlegen gekuerzt wurden)
3. kein Treffer → neuer Task

Haerten heisst hier: **deterministisch werden.** Heute nimmt `existingTasks.find(...)`
bei mehreren gleichnamigen Tasks den erstbesten in Listenreihenfolge — die haengt
an `position`, die sich beim Verschieben aendert. Derselbe Sync kann also je nach
Board-Zustand einen anderen Task treffen. Festlegen: bei mehreren Treffern gewinnt
der **aelteste nicht archivierte** (`created_at ASC`), archivierte Tasks werden
nie getroffen. Und: ein bereits in diesem Lauf getroffener Task darf nicht
ein zweites Mal matchen, sonst kollabieren zwei gleichnamige Todos auf einen Task.

**Bekannte, nicht behebbare Einschraenkung:** wird ein Task im TUI umbenannt,
erzeugt der naechste Sync einen zweiten Task. Gehoert in README und CHANGELOG,
nicht in den Bugtracker.

**d) Eine Transaktion:** die gesamte Schleife in `db.transaction(...)`. Heute wird pro Task einzeln geschrieben; ein Fehler in der Mitte hinterlaesst einen halb synchronisierten Zustand.

**e) Reconcile** — unveraendert beschlossen.
Sync meldet den *Zielzustand*, nicht den Weg. `TransitionService.reconcilePath(ist, soll)` berechnet die Zwischenschritte, jeder wird als eigene Transition mit `reported_by = "sync"` und `reason = "reconcile"` protokolliert.

Neue Tasks entstehen in `todo` und werden von dort weiterbewegt — nicht direkt in der Zielspalte angelegt. Ein Todo, das erstmals mit `completed` auftaucht, erzeugt also: Entstehung in `todo`, dann `todo→in-progress→review→done`. Vier Transitions. Das ist gewollt: die Kette soll die Historie erzaehlen, auch wenn sie in einer Sekunde durchlaufen wird.

Mit dem Wegfall von `cancelled` bleiben genau drei Zielspalten: `todo`,
`in-progress`, `done`. Alle drei sind vorwaerts erreichbar; `reconcilePath`
laeuft in diesem Pfad nie rueckwaerts, ausser wenn ein Agent einen Todo von
`completed` auf `in_progress` zuruecksetzt — dann ein direkter Rueckwaertssprung,
immer erlaubt.

**Verschwundene Todos werden ignoriert — bewusst.** TodoWrite ersetzt bei jedem
Aufruf die ganze Liste, ein fehlendes Todo koennte also "abgebrochen" heissen.
Es koennte aber genauso gut heissen, dass der Agent die Liste gekuerzt hat oder
eine neue Aufgabe begonnen hat. Die beiden Faelle sind aus dem Payload nicht
unterscheidbar, und die falsche Annahme wuerde Tasks aus dem Board raeumen, die
JoPa noch braucht. Der Sync loescht und archiviert nichts — wie bisher.

**f) WIP-Verstoesse werden geloggt, nicht abgelehnt.** TodoWrite ist nicht ablehnbar — der Agent hat den Zustand bereits gesetzt, der Hook laeuft danach. Ein Verstoss erzeugt:
- Transition mit `was_override = 1`, `reason = "wip-exceeded (sync)"`
- Zeile auf stderr
- TUI-Sichtbarkeit: WIP-verletzte Spalten bekommen im Header `3/3 ⚠` in Warnfarbe (`theme.ts`)

**g) Keine Priority-Uebernahme.** Das Feld existiert im Payload nicht
(Abschnitt 0.1). `priority` wird ausschliesslich manuell gesetzt.

**h) Schema-Guard:** meldet und beendet mit Exit 0 (2.2).

**i) Datei bleibt unter 300 Zeilen.** Wenn nicht: Reconcile-Logik nach `src/core/sync-service.ts`, `sync.ts` bleibt reine CLI-Huelle (stdin lesen, parsen, Bericht ausgeben). Das ist wahrscheinlich der bessere Schnitt — dann ist die Sync-Logik auch testbar, ohne stdin zu simulieren. **Empfehlung: von Anfang an so bauen.**

### 5.1 Registry

(`docs/decisions/0003-kanban-verzeichnis-ist-reserviert.md`). Die Regel gilt ueber


Nur `path` ist Wahrheit — `name` ist ein Cache aus der `config.json` und wird beim Lesen aufgefrischt. Boards, deren Pfad nicht mehr existiert, werden beim Lesen als `missing` markiert, aber **nicht automatisch entfernt** (ein ausgehaengtes Netzlaufwerk ist kein geloeschtes Board).

die tragende Festlegung der Entscheidung: `tests/helpers.ts:24` ruft `initBoard()`
bei jedem Testlauf auf und legt ein temporaeres Board an. Wuerde `initBoard()`
registrieren, waere die Registry nach einer Woche Entwicklung voller toter
`/var/folders/...`-Pfade. Dieselbe Trennung schuetzt `importBoard()`, das
`createSchema()` ebenfalls direkt aufruft. Zusaetzlich `kanban init --no-register`.

**Atomar schreiben** (tmp + rename), damit zwei gleichzeitig laufende Prozesse
die Datei nicht zerreissen.

## 9. Einwaende des Planers

Alle fuenf sind vom Teamlead beschieden. Stand hier eingearbeitet.

**E-1 — `source_id` aus `TodoItem.id`: BESTAETIGT, Feld existiert nicht.**
Die Grilling-Zusammenfassung nannte die TodoWrite-IDs "moeglicherweise nicht session-stabil". Der Befund ist haerter: das Feld wird gar nicht geliefert, ebensowenig `priority`, ebensowenig der Status `cancelled`. Belegt aus drei unabhaengigen Quellen (Abschnitt 0.1). Die Deklaration in `sync.ts:16-22` entspricht einer fruehen oeffentlich kursierenden Fassung und wurde nie validiert, weil `sync.ts` nie fehlerfrei durchgelaufen ist.

Folgen: `source_id` gestrichen, P2-4 gestrichen, P1-7 neu zugeschnitten. Reconcile und Transaktion bleiben unveraendert beschlossen.

**Was daraus zu lernen ist:** eine Typdeklaration in einem Codepfad, der nie ausgefuehrt wurde, ist eine Behauptung. Der Fall ist hier zweimal aufgetreten (Interface *und* toter `cancelled`-Zweig) und beide Male in derselben Datei — derselben, die auch den Konstruktorfehler traegt. Ungetesteter Code altert nicht, er verrottet.

**E-2 — Upward-Search fuer `kanban sync`: ENTSCHIEDEN, sucht nicht aufwaerts.**
`sync` ist technisch ein CLI-Kommando, semantisch ein automatischer Hook — er laeuft unbeaufsichtigt mit einem `cwd`, den Claude Code setzt. Genau die Konstellation, fuer die die exakte Suche als Isolationsgrenze zwischen Projekten beibehalten wurde. Eine Aufwaertssuche wuerde bewirken, dass ein Agent im Unterprojekt seine Todos still in das Board des Elternprojekts schreibt. Eingearbeitet in Abschnitt 5.4 und in Task P3-2.

**E-3 — `cancelled → backlog` widerspricht der Backlog-Regel aus CLAUDE.md. ERLEDIGT: der Fall existiert nicht.**
TodoWrite kennt keinen Status `cancelled` (Abschnitt 0.1). Der Zweig in `STATUS_TO_COLUMN` (`sync.ts:13`) ist toter Code und wird entfernt. Der Sync schreibt damit nie ins Backlog.

Die urspruengliche Beurteilung bleibt fuer den verbleibenden Fall gueltig: `addTask` ins Backlog ist ueber `allowEntry: true` weiter moeglich, und die CLAUDE.md-Regel "Agents schreiben nie direkt ins Backlog" ist eine **Arbeitsanweisung, keine Werkzeugregel** — eine Rollenpruefung waere self-reported und damit nicht durchsetzbar (dieselbe Begruendung wie in ADR 0002 fuer `force` nach Rollennamen).

**E-4 — Die vier Transitions eines frisch-fertigen Todos sind Fiktion.**
Ein Todo, das erstmals als `completed` auftaucht, bekommt eine Historie `todo→in-progress→review→done` mit vier Zeitstempeln innerhalb derselben Sekunde. Das ist ein bewusster Preis fuer die Kettenintegritaet und in Ordnung — aber wer die Transitions spaeter fuer Durchlaufzeiten auswertet, misst Unsinn. `reason = "reconcile"` markiert diese Eintraege, damit man sie herausfiltern kann. Bitte beim Bauen nicht wegoptimieren.

**E-5 — Der Guard blockiert auch den Sync-Hook.**
Bei Schema < 3 beendet sich Sync mit Exit 0 und einer stderr-Meldung. Das ist richtig, hat aber eine Konsequenz: solange JoPa nicht migriert, laeuft der Hook bei jedem TodoWrite ins Leere, und die Meldung geht im Rauschen unter. Kein technisches Problem — aber ein guter Grund, `kanban migrate` gleich nach dem Merge von Paket 0 auf allen eigenen Boards auszufuehren.
